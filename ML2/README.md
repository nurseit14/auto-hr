# ML2: предразметка и обучаемый реранкер резюме–вакансия

Модуль сам выбирает **5 разных вакансий для каждого резюме**, вызывает языковую
модель, оценивает каждое требование и общую пригодность, затем загружает готовые
предложения в отдельный проект Label Studio. Человек проверяет и исправляет их.

После проверки отдельный локальный реранкер обучается сортировать вакансии по
итоговым оценкам. `ML2.model` вызывает GPT для предразметки; `ML2.ranker` —
обучаемая линейная модель для сортировки. Это разные компоненты.

## Запуск

Из корня AUTO-HR, в существующем окружении проекта:

```bash
./.venv-label-studio/bin/python -m ML2.run --publish
```

Для установки в новом окружении: `python -m pip install -r ML2/requirements.txt`.
Для публикации нужен также установленный `label-studio` и вход в локальный аккаунт.

Ключ читается из `.env` в корне проекта (`OPENAI_API_KEY`), не сохраняется в результатах.
Тексты резюме и вакансий отправляются в OpenAI API. По умолчанию используется
`gpt-4.1-mini-2025-04-14`, без дообучения; модель задаётся `--model` или `ML2_MODEL`.
В запросах установлено `store=False`. Ограничения и ошибки извлечения исходного
CSV сохраняются: модуль не восстанавливает отсутствующий текст PDF.

Проверка на вымышленных данных:

```bash
./.venv-label-studio/bin/python -m ML2.run --demo --output-dir data/annotations/ml2_demo_v1
```

Подготовить список пар без вызова платного API:

```bash
./.venv-label-studio/bin/python -m ML2.run --prepare-only
```

Повторный запуск с теми же данными использует кэш. Изменение текста, схемы,
инструкции или модели меняет ключ кэша. Для другого набора/модели/даты задайте
новый `--output-dir`. Публикация добавляет только отсутствующие пары и никогда
не заменяет ручную разметку. При продолжении в другой день дата расчёта стажа
автоматически берётся из `manifest.json`. Для нового эксперимента можно явно
задать `--reference-date YYYY-MM-DD` и новый `--output-dir`.

## Оценки

| Балл | Смысл требования |
| --- | --- |
| 0 | Недостаточно сведений: навык/опыт не подтверждён и не опровергнут |
| 1 | Подтверждённое несоответствие, например Junior при требовании Middle |
| 2 | Частичное соответствие |
| 3 | Соответствие по данным резюме |

Общая оценка: 0 — недостаточно данных, 1 — слабое соответствие, 2 — частичное,
3 — хорошее. Она объясняется отдельно и не равна среднему баллов.
Условие «1–3 года» включает ровно 1 год. Отсутствие Python в резюме даёт 0,
а не утверждение, что кандидат не знает Python.

Модель обрабатывает все сохранённые тексты целиком, без скрытого обрезания.
Выделяет роль/уровень, опыт, отдельные технологии, языки, образование и другие
явные требования. Каждая оценка содержит объяснение и точную цитату из вакансии;
баллы 1–3 требуют точной цитаты из резюме. Проверка цитат автоматическая;
корректность интерпретации проверяет человек. Пустое резюме остаётся в наборе:
пять пар с неизвестными оценками и предупреждением, без выдуманных фактов.

## Входные данные и выбор пар

- `data/resumes/processed/resumes.csv`: `resume_id`, `text`, необязательный `skills`.
- `data/processed/vacancies_with_skills.csv`: `vacancy_id`, `title`, `requirements`,
  `experience`, `responsibilities`, `text`, необязательный `skills`.

Текущая версия выбирает пять наиболее близких вакансий с помощью локального
BM25 и пересечения словарных навыков. Выбор воспроизводим и не требует готового
индекса ML1. Это способ подготовки пар для разметки, а не метрика качества поиска.
Все пять вакансий различаются по ID и сохранённому содержанию.
Пути можно переопределить через `--resumes` и `--vacancies`.

## Результаты и Label Studio

Результаты по умолчанию: `data/annotations/ml2_auto_v1/` (закрытые данные,
уже исключены из Git правилами проекта):

- `manifest.json` — ID всех пар, хеши источников и параметры;
- `cache/` — структурированные ответы модели и версии;
- `tasks_with_predictions.json` — готовый импорт Label Studio;
- `label_config.xml` — интерфейс проверки;
- `summary.json`, `failures.json` — полнота обработки, баллы и ошибки;
- `label_studio_project.json` — ссылка на созданный проект.

На странице разметки нажмите на выделенное требование, измените оценку,
объяснение или цитату. Можно удалять лишние выделения и добавлять пропущенные
прямо в тексте вакансии. Проверьте общую оценку, поставьте отметку ручной проверки
и нажмите **Submit**. Модель не ставит эту отметку и не создаёт готовые человеческие
аннотации. До проверки предсказания не считаются эталонной разметкой.

## После проверки: подготовка набора для реранкера

Из Label Studio нужен полный экспорт **JSON**, сохраняющий исходные тексты,
границы выделений и `annotations[].result`. Формат JSON-MIN для этой команды
не подходит. Экспорты `ML2/project-*.json` и результаты в `data/annotations/`
исключены из Git: они содержат частные резюме.

Подготовка работает локально, не вызывает API, не меняет разметку и не обучает
модель. Пример для проверенной выгрузки проекта 6:

```bash
./.venv-label-studio/bin/python -m ML2.prepare_dataset \
  --export ML2/project-6-at-2026-10-26-07-44-6c15c0c0.json \
  --output-dir data/annotations/ml2_training_v1 \
  --same-candidate resume_0009,resume_0010 \
  --seed 42
```

`--same-candidate` объединяет подтверждённые версии резюме одного человека;
его можно повторить для других групп. Для текущего набора два указанных CV
принадлежат одному кандидату. Одинаковые непустые тексты объединяются также
автоматически. Похожие шаблоны без подтверждения личности не объединяются.
Готовая непустая папка не перезаписывается: для нового запуска задайте новую
версию, например `data/annotations/ml2_training_v2`.

Команда проверяет пять разных вакансий на каждый CV, версии исходных текстов,
границы выделений, типы требований, оценки, объяснения и цитаты. При нескольких
сохранённых аннотациях одной пары выбор не делается автоматически — сначала
нужно разрешить неоднозначность. Предсказания и `data.model_assessment` не
используются как итоговые оценки. Пробельные различия в цитате допускаются,
затем цитата восстанавливается из оригинального текста; другие изменения
не допускаются.

Файлы результата:

- `pairs_all.jsonl` — все пары, оригинальные тексты и сохранённая разметка;
- `requirements_all.jsonl` — отдельные требования, оценки, объяснения и цитаты;
- `train.jsonl`, `validation.jsonl`, `test.jsonl` — ID пар и целевые оценки;
- `quarantine.jsonl` — пары с пустым CV или неизвестной общей оценкой;
- `candidate_groups.json`, `split_assignment.json` — группировка и разделение;
- `manifest.json`, `quality_report.json` — происхождение, настройки и проверки.

**0 означает неизвестность, а не плохое соответствие.** Исходная общая оценка
сохраняется в `overall_score`. Для последующего ранжирования вводится отдельная
релевантность: слабое соответствие 1 → 0, частичное 2 → 1, хорошее 3 → 2;
неизвестность 0 → `null` и исключение из обучения/оценки ранжирования.
У требований также сохраняются исходный балл, статус и `judged`; неизвестные
требования нельзя автоматически превращать в отрицательные примеры.

Версии резюме одного кандидата целиком остаются в одной части. Разделение
воспроизводимо и учитывает распределение оценок. Это проверка на **новых
кандидатах**: вакансии между частями могут повторяться. Оценка будет относиться
к пяти размеченным вакансиям, а не к поиску по всему каталогу. Чекбокс аккаунта
не доказывает независимую человеческую проверку; смешанная проверка Куатом и
ассистентом записывается в происхождении текущего набора.

Зафиксированный пилот: 220 пар, 44 версии CV, 1 542 требования. Пять пар пустого
CV сохранены отдельно. Остальные 215 разделены на 155 обучающих, 30 для настройки
и 30 для итоговой проверки. Кандидаты между этими частями не пересекаются.
Полное соответствие получило только 10 пар, поэтому это небольшой пилот.

В файлах разделения намеренно нет готовых признаков: оценки, объяснения и цитаты
разметки не должны попадать на вход модели. Исходные тексты сохраняются для
проверки происхождения. Обучение реранкера командой подготовки не выполняется.

## Локальный обучаемый реранкер

Первая версия — **линейное попарное ранжирование с L2-регуляризацией**.
Для одного CV берутся две вакансии с разными итоговыми оценками; модель учится
давать больший балл более подходящей. Вес каждого резюме в функции потерь
нормируется, чтобы число сравнимых пар не давало ему непропорциональный вес.
Это не fine-tuning GPT и не нейросеть CrossEncoder.

Модель получает 12 фиксированных профессиональных сигналов из **исходных** CV
и вакансии: совпадения технологий и задач, профиль работы, явный уровень,
указанный общий стаж, образование, явно заданные языковые уровни, отрасль и
коммуникацию. Имена, контакты, пол, возраст и гражданство не являются признаками;
свободного словаря слов из резюме нет. Известные строки шаблонных инструкций
удаляются. Объяснения, цитаты и оценки разметки не используются как признаки.
Список признаков фиксирован, их веса учатся только на train; нулевой вес означает,
что данный сигнал не помог обучению на этом небольшом наборе.

Рабочий стаж учитывается только по явно заявленному общему числу лет. Если его
нет, даты учёбы и отдельные интервалы работы не превращаются в догадку о стаже.
Язык сравнивается только при наличии указанного уровня с обеих сторон. Словарные
совпадения — ограниченный сигнал, а не воспроизведение всех суждений разметчика.

Масштабирование признаков оценивается на train. Коэффициенты неотрицательны:
увеличение совместимости не должно ухудшать балл при остальных равных.
Сила регуляризации выбирается по validation. Test не участвует в подборе.
Результат — **относительный балл сортировки**, не вероятность найма и не
автоматическая оценка по шкале 0–3.

Обучить новый эксперимент (папка результата должна быть новой):

```bash
./.venv-label-studio/bin/python -m ML2.train \
  --dataset data/annotations/ml2_training_v1 \
  --output-dir data/annotations/ml2_reranker_v2
```

Уже обученная первая версия находится в `data/annotations/ml2_reranker_v1/`:

- `model.json` — изученные веса, масштабирование и происхождение модели;
- `evaluation.json` — результаты обучения, настройки и отдельного теста;
- `test_predictions.jsonl` — оценки тестовых пар;
- `report.txt` — короткий отчёт по-русски.

В первой версии обучение использовало 155 пар и 132 сравнения вакансий. На тесте
из шести CV / 30 пар NDCG@5: исходный BM25/skills-порядок — **0.6735**, простое
покрытие навыков — **0.6990**, обученный ML2 — **0.7391**. Это результат небольшого
пилота, не процент правильных решений и не проверка по всему каталогу вакансий.
Сравнение с выполненным ML1 embedding-поиском ещё не проведено: исходный порядок
размеченных пяти вакансий получен другим модулем. Test-вакансии могут повторяться
в train; кандидаты между частями не пересекаются.

Метрика использует линейную релевантность 0/1/2, усредняет равные предсказанные
баллы и отдельно показывает запросы с различающимися оценками. Запросы, у которых
все вакансии имеют слабую релевантность 0, исключаются из NDCG, а не объявляются
идеально отсортированными. Метод попарной функции потерь описан в
[Learning to Rank using Gradient Descent](https://www.microsoft.com/en-us/research/publication/learning-to-rank-using-gradient-descent/);
в этой реализации используется линейная функция оценки. Определение метрики:
[DCG / NDCG](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.dcg_score.html).

Проверить сохранённую модель без переобучения:

```bash
./.venv-label-studio/bin/python -m ML2.evaluate
```

Посмотреть пример на сохранённых пяти вакансиях:

```bash
./.venv-label-studio/bin/python -m ML2.rerank --cv-id resume_0005 --brief
```

Для нового резюме передайте UTF-8 текст и JSON-список или CSV уже выбранных
вакансий: `--cv resume.txt --vacancies shortlist.json`. По умолчанию выдаётся JSON;
`--brief` выводит короткий текст. `--output` сохраняет результат в новый файл.
Пустое резюме отклоняется. Пять неизвестных пар исходного набора не обучают модель.

Программное подключение после ML1:

```python
from ML2.ranker import LinearRanker

model = LinearRanker.load("data/annotations/ml2_reranker_v1/model.json")
# shortlist — результат matcher.match(resume_text, top_k=20)
ranked = model.rerank(resume_text, shortlist, top_k=5)
```

Исходные ID и баллы ML1 сохраняются, добавляются `ml2_score`, профессиональные
сигналы и их вклады. Автоматическое включение в ML1 не выполнено: компонент
принимает его результат через этот интерфейс. Реранкер не создаёт новые
выделения и цитаты для Label Studio — за предразметку по-прежнему отвечает
`ML2.model`. При изменении кода признаков или словаря сохранённая модель
отклоняется до переобучения; для повторной оценки проверяются хеши набора.

Новые файлы: `features.py` — признаки, `ranker.py` — обучение и модель,
`metrics.py` — метрики, `train.py` — эксперимент, `evaluate.py` — повторная
проверка, `rerank.py` — применение. Проверки: `tests/test_reranker.py`.

Сервер запускается локально при `--publish`, если ещё не запущен.
Существующие проекты сохраняются. На этом компьютере модуль получает
краткоживущий JWT доступа единственного пользователя локальной базы.
Пароли и настройки безопасности не меняются. Для другого сервера задайте
`LABEL_STUDIO_API_KEY` (access JWT или legacy API token) и `--label-studio-url`.
Публикация готового результата без вызова модели:

```bash
./.venv-label-studio/bin/python -m ML2.run --publish-only
```

Проверки кода без API: `./.venv-label-studio/bin/python -m unittest discover -s ML2/tests -v`.

Форматы интеграций: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs),
[Label Studio pre-annotations](https://labelstud.io/guide/predictions.html).
